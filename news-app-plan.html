01方案概览

核心逻辑一句话：定时抓取多家权威媒体 → 去重并把同一事件的多篇报道聚成一条 → 调用大模型生成中英双语的「一句话摘要 + 详细解读」→ 写入数据库 → 前端按分类展示。

整套系统每天只在固定时间跑一次批处理，前端读的是已经处理好的静态数据，因此打开速度极快，服务器成本接近于零。

02平台选择：先做 PWA，不建议一上来做微信小程序

方案优点代价
PWA 网页应用
（推荐）		手机浏览器直接打开，可「添加到主屏幕」，图标和体验接近原生 App；无需审核，改完就上线；开发只需一套 Web 技术栈iOS 推送支持较弱（16.4+ 才支持）
微信小程序微信内分享传播方便新闻资讯类目需要《互联网新闻信息服务许可证》，个人主体基本无法通过审核；还需域名备案、ICP 备案
原生 App体验最好开发量大，上架审核同样涉及新闻资质
合规提醒：在国内，「转载新闻」本身是受许可管理的。个人项目建议定位为自用 / 小范围分享的信息聚合工具，并且严格做到：只展示自己生成的摘要，不全文转载原文，每条都附原文链接跳转回源站。这样既避开版权问题，也降低合规风险。

03系统架构

① 采集 Collector　RSS / API 抓取 → 原始文章入库
　　　↓
② 清洗 Cleaner　正文提取、去广告、语言识别
　　　↓
③ 聚合 Clusterer　标题向量化 → 同事件多源合并成一个 story
　　　↓
④ 加工 Enricher　LLM 一次调用产出：分类 + 中英标题 + 中英摘要 + 中英详情 + 重要度
　　　↓
⑤ 发布 Publisher　生成当日 JSON / 写入数据库
　　　↓
⑥ 前端 Web App　分类浏览 → 点击展开详情

04新闻源清单

以 RSS 为主、API 为辅。RSS 免费、稳定、无配额限制；API 用来补充 RSS 覆盖不到的源。

区域源方式

05分类体系

建议固定 7 类，不要太多，手机上一屏能扫完最重要：

  1. 国际时政 World & Politics
  2. 经济财经 Business & Economy
  3. 科技 Technology
  4. 冲突与安全 Conflict & Security
  5. 科学健康 Science & Health
  6. 社会文化 Society & Culture
  7. 中国 China

每类当天保留 5–10 条，由模型给出的 importance 分数（1–10）排序截断。全站每天 40–60 条，阅读量适中。

06大模型加工环节

关键设计：一次调用产出全部字段，不要分成「先摘要、再翻译、再分类」三次调用，成本和延迟都会翻倍。

提示词骨架

你是一名专业的国际新闻编辑。下面是关于同一事件的 N 篇报道。
请交叉核对信息，忽略各源的立场倾向，只保留能相互印证的事实。

要求：
1. 分类：从 [国际时政|经济财经|科技|冲突与安全|科学健康|社会文化|中国] 中选一个
2. 重要度：1-10 分，考虑影响范围、紧迫性、长期意义
3. 摘要：中英文各一句，不超过 45 字 / 30 words，说清「谁做了什么、结果如何」
4. 详情：中英文各 250-350 字，结构为——事件经过 / 背景脉络 / 各方反应 / 可能影响
5. 若各源说法存在冲突，在详情中明确指出分歧

只输出 JSON，不要任何解释文字或 Markdown 代码块。

输出结构

{
  "category": "国际时政",
  "importance": 8,
  "title_zh": "……",
  "title_en": "...",
  "summary_zh": "……",
  "summary_en": "...",
  "detail_zh": "……",
  "detail_en": "...",
  "tags": ["欧盟", "能源政策"],
  "sources": [
    {"name": "Reuters", "url": "https://..."},
    {"name": "BBC", "url": "https://..."}
  ]
}

用 JSON Schema / structured output 模式约束返回格式，解析失败就重试一次，仍失败则丢弃该条。

07数据库结构

-- 原始文章（仅作聚类和溯源用，可定期清理）
articles(
  id, source_name, url, title, content,
  published_at, fetched_at, lang, embedding vector(384)
)

-- 处理后的事件，前端只读这张表
stories(
  id, date,                    -- 当天日期，用于按日查询
  category, importance,
  title_zh, title_en,
  summary_zh, summary_en,
  detail_zh, detail_en,
  tags jsonb,
  sources jsonb,               -- [{name, url}]
  image_url,                   -- 取首源的 og:image
  created_at
)

索引：(date, category, importance DESC)

08页面与交互

三个页面就够

  • 首页（列表）：顶部日期 + 语言切换；分类作为横向 tab；下方是卡片流。卡片只显示中英标题和一句话摘要。
  • 详情页：完整中英解读，底部列出所有原文来源链接。从列表点击后滑入。
  • 归档：按日期回看往期，支持关键词搜索。

双语呈现方式

推荐 「中文为主 + 英文副标题」的默认模式，而不是左右分栏（手机上太挤）。顶部提供三挡切换：中 / 中英 / EN。详情页里中英文段落上下交替排列，方便对照学习。

细节

  • 每条摘要下方显示来源数量，如「综合 4 家报道」，体现交叉核实
  • 重要度 ≥ 8 的条目标题前加一个小圆点作为标记，不用红色徽章
  • 支持长按分享单条为图片
  • 离线缓存当天数据（Service Worker），地铁里也能看

09视觉规范

方向：报刊质感的极简——大留白、细分隔线、不用阴影、圆角控制在 4–6px、靠字体和字重建立层次，而不是靠颜色和色块。

字体

  • 中文正文：系统默认无衬线（PingFang SC / 思源黑体），保证长文可读
  • 英文：Inter 做界面和正文，标题可用 Newsreader 呼应中文宋体
  • 字号：标题 19px / 正文 15px / 摘要 13px / 元信息 11px，行高 1.6–1.75

11实施路线

阶段一：跑通数据（约 2–3 天）

写一个 Python 脚本：抓 10 个 RSS 源 → 取标题和摘要 → 丢给模型 → 打印 JSON。不碰前端、不碰数据库，先确认「生成的内容质量能看」。这一步最关键，内容不行后面都白做。

阶段二：加上去重和存储（约 2 天）

接入向量聚类合并同事件，结果写入 Supabase，并配好 GitHub Actions 每天定时跑。

阶段三：前端（约 3–4 天）

Next.js 搭列表页 + 详情页，实现分类切换和语言切换，套上面的视觉规范，部署到 Cloudflare Pages。

阶段四：打磨（持续）

加 PWA manifest 和离线缓存、归档搜索、分享成图；根据实际阅读体验调整提示词里的摘要长度和分类粒度。

12容易踩的坑

  • 模型会编造细节。 提示词里必须强调「只使用给定材料中的信息，不确定的写不确定」，并且详情页一定要附原文链接让读者可核。
  • 聚类阈值需要调。 太松会把不相关的新闻合并，太紧则同一事件重复出现。建议先人工看一周的聚类结果再定参数。
  • RSS 源会挂。 单源抓取失败要静默跳过，不能让整个流程中断；记录失败次数，连续失败就告警。
  • 翻译不等于改写。 让模型「基于事实重写」而不是「逐句翻译」，中文才读得顺。
  • 不要贪多。 每天 50 条是上限，超过就没人看得完，这类产品的价值恰恰在于「帮我筛掉 95%」。
